## Work items, in priority order

### WI1 — Supervisor lifecycle log

The Rust supervisor keeps only a bounded in-memory output tail that disappears
when the wrapper quits. During the reproduction there was no engine application
log at all under the canonical `logs/` directory, so a lifecycle fault cannot be
diagnosed after the fact.

Add a bounded, rotating log written by the wrapper to
`<canonical root>/logs/desktop-supervisor.log`. The canonical root is what
`church_cap_data_dir` returns in `lifecycle.rs`.

Record, one line per event with a UTC timestamp:

- wrapper PID and version at launch;
- the absolute engine executable path and the canonical data directory selected
  at spawn, and whether a legacy-folder migration ran (the
  `LegacyMigrationSummary` counts, not file names);
- child PID and every `SupervisorPhase` transition, with the detail string;
- each command sent over the protocol by name only (no arguments), the stop
  deadline, whether a forced kill was used, and the child's exit code;
- the health-confirmation result and the two port numbers;
- the runtime-configuration path, modification time and a content hash, never
  its contents;
- stdout/stderr lines needed to explain a failed start or stop, passed through
  the same redaction the in-memory tail already applies.

Never log passwords, session tokens, authentication file contents, caption or
transcript text, private keys, full environment variables, request bodies, or
home-directory paths beyond the two selected paths above.

Rotation is owned by Rust because Rust holds the file open. Match the Python
policy in `app/storage.py` `rotate_log_file` (5 MB, two backups) but implement
it in the writer: check size before each append, rename `.log` → `.log.1` →
`.log.2`. Do **not** add this file to `rotate_runtime_logs` in `app/storage.py`;
renaming a file another process has open fails on Windows.

Expose it through the existing support path: add
`"desktop-supervisor.log": _tail_log(support_logs_dir / "desktop-supervisor.log")`
to the `logs` block of `diagnostics_payload()` in `app/main.py` (around line
1634). `_tail_log` is already byte-bounded and redacts local paths. Update the
`privacy_note` string in the same payload to mention supervisor lifecycle lines.

Put the writer in its own module (`desktop/src-tauri/src/supervisor_log.rs`),
keep it free of Tauri types so it can be unit-tested with a temporary
directory, and have `lifecycle.rs` call it from the existing `publish` path so
every transition is captured in one place rather than at each call site.

### WI2 — Privacy-safe instance identity in diagnostics

The incident handoff's first two hypotheses were "the browser and wrapper may
be observing different processes" and "the save and the next start may use
different data roots". Nothing in the product can currently prove they agree.

Add to the authenticated diagnostics payload (`diagnostics_payload()`), not to
the public `/health`, which `tests/test_security_controls.py` requires to stay
minimal:

- engine PID (`os.getpid()`);
- supervisor PID from the `CHURCH_CAP_SUPERVISOR_PID` environment variable the
  wrapper already sets at spawn (`lifecycle.rs`, engine `Command` env), or
  `null` for a source run;
- a data-root fingerprint: the first 16 hex characters of SHA-256 over the
  canonical data-directory path string, never the path itself;
- `runtime_config.json` modification time and the same content-hash form used
  by WI1, so the wrapper log and the engine agree on one value;
- a short random instance identifier generated at engine start and held in
  memory.

Surface the same fingerprint, instance identifier and engine PID in the
wrapper's Service details panel (`desktop/src/index.html` around the `enginePid`
row and `desktop/src/main.js` render) by reading them from the engine after
health confirmation. That makes "the Operator page, `/health`, the wrapper and
the settings file belong to the same engine" a thing a person can check in ten
seconds rather than a thing that needs `lsof`.

### WI3 — Packaged-engine save-then-restart check through the real API

`scripts/release/check-settings-restart.py` writes `runtime_config.json` before
starting the engine and reads it back after a restart. It proves the file
survives; it does not prove the authenticated browser save path writes it.
Extend the script, keeping the existing pre-written case as a second mode:

1. In the isolated data directory, set `OPERATOR_PASSWORD` in the engine's
   environment to a random value for that run (`app/settings.py` reads it and
   `bootstrap_auth_store` seeds the store). Never reuse a real password.
2. Log in the way the browser does: `GET /login` to receive the form CSRF cookie
   and the hidden `csrf_token` field, then `POST /login` with both. Keep the
   session cookie.
3. Read the `church-cap-csrf-token` meta tag from `GET /operator` and send it as
   the `X-CSRF-Token` header (see `app/templates/operator.html` lines 6 and 38
   and `require_operator_mutation` in `app/auth.py`).
4. `POST /api/translation` with a Restricted English + French body, then with a
   translation-Off body while languages remain selected.
5. After each save, assert the primary file, the backup file, the response body
   and the public `/api/languages` agree; then shut down through the protocol,
   start again with the same directory, and assert the same four sources still
   agree.

The script must exit non-zero on any disagreement and print which of the four
sources differed. Keep it dependency-free beyond the standard library, as it is
now, so it runs against each frozen platform engine.

### WI4 — Native supervisor lifecycle self-test

`run_self_test_if_requested` in `lifecycle.rs` (debug builds only) already runs
Ready → forced stop → automatic recovery → stop when
`CHURCH_CAP_SUPERVISOR_RECOVERY_SELF_TEST=1`. Nothing exercises the manual
Stop, Start and Restart paths, which is what the owner uses.

Add `CHURCH_CAP_SUPERVISOR_LIFECYCLE_SELF_TEST=1` to the same function. It must
run, in order, with a bounded deadline on each step and a distinct
`CHURCH_CAP_SUPERVISOR_LIFECYCLE_TEST=<result>` line on failure:

1. wait for Ready with health confirmed, record PID A;
2. `request_stop`, wait for Stopped, then assert both ports refuse a TCP
   connection (attempt a connect to 127.0.0.1 on each; a refusal is the pass);
3. `start`, wait for Ready, assert a new PID B ≠ A;
4. the manual restart path used by the Restart button, wait for Ready, assert
   exactly one new PID C ≠ B and that B is no longer running;
5. `request_stop`, wait for Stopped, print `…=passed`, exit 0.

Add two debug-only environment overrides next to the existing
`CHURCH_CAP_ENGINE_PATH` override in `resolve_engine_path`:
`CHURCH_CAP_DESKTOP_DATA_DIR` (used instead of `church_cap_data_dir`) and
`CHURCH_CAP_DESKTOP_LEGACY_DATA_DIR` (used instead of `legacy_tauri_data_dir`).
Both must be `#[cfg(debug_assertions)]` so a release build cannot be pointed at
another user's folder. With those, add `scripts/release/check-desktop-lifecycle.py`
that seeds a legacy folder with an `operator_auth.json` and a Restricted
English + French `runtime_config.json`, launches the debug wrapper with the
lifecycle self-test, and asserts afterwards that the canonical folder holds the
migrated files plus `data/legacy_data_migration.json`, that the legacy folder
holds only `MOVED-TO-CHURCH-CAP.txt`, and that the public language state read
during the run was Restricted English + French. This is the installed-wrapper
proof the migration currently lacks. It needs a display session, so document
it as a release-Mac check rather than a CI job.

### WI5 — Operator page: honest unsaved state (optional, low)

Once a control is changed, `operatorTranslationEditing` suppresses the
1.5-second poll until a save succeeds (`app/templates/operator.html`
`syncOperatorTranslationControls` and the `change` listeners near line 5177).
A save that fails with a network error therefore leaves the page showing edited
values indefinitely while the server disagrees, which is what made the Off
refusal look like a persistence fault. If you take this item: show a visible
"Unsaved changes" state on the language panel while the guard is active, add a
"Discard changes" control that clears the guard and re-syncs from the server,
and after a failed save keep the guard but make the failure line persistent
until the next attempt. Do not auto-discard edits on a timer.

## Constraints and invariants

- **Privacy boundary.** No audio, caption, transcript or translation wording,
  no passwords, session secrets, `.env` contents, private keys, or full local
  paths in any log or diagnostics field. `diagnostics_payload()` redacts paths
  through `_tail_log`; new fields must not reintroduce them.
- **Public `/health` stays minimal.** `tests/test_security_controls.py`
  asserts its shape. Identity fields go in authenticated diagnostics only.
- **Security boundary ordering.** `security_boundary_middleware` before
  `browser_security_headers`; the same test file asserts it by index.
- **Public viewer routes stay wrapped in `_no_cache`.** Same test file.
- **No outbound network.** Church Cap is inbound only. Nothing here needs a
  socket that is not loopback.
- **Migration semantics are fixed.** Do not change the guards in
  `legacy_root_needs_migration` or the rollback behaviour; add overrides around
  them, not inside them.
- **Debug-only overrides must be `#[cfg(debug_assertions)]`.** A release build
  must ignore `CHURCH_CAP_DESKTOP_DATA_DIR` and
  `CHURCH_CAP_DESKTOP_LEGACY_DATA_DIR` entirely.
- **No version bump, no updater, signing, notarization or `dist/` changes.**
- **Structure tests.** `tests/test_cross_platform_structure.py` parses
  `lifecycle.rs` and `recovery.rs` textually; keep the asserted lines intact
  (`let data_dir = church_cap_data_dir(app)?;`, the migration call preceding
  `Command::new`, the three guard expressions).
