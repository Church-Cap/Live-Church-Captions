# Church Cap v0.9.0 Implementation Record

## Release focus

v0.9.0 introduces a named ProPresenter presentation workflow while keeping Church Cap local-network first. It builds on the existing transparent `/obs` output rather than adding an outbound ProPresenter API, plugin, account, or cloud dependency.

## Operator experience

The Operator dashboard now includes **Congregation → ProPresenter** with:

- a plain-language six-step Prop setup guide;
- a selector containing English and locally installed caption languages;
- a matching search field for quickly narrowing a long installed-language list;
- a generated direct-IP URL with a fixed `lang` value;
- copy, preview, and full-guide actions;
- live connected/not-connected status and the language of each connected ProPresenter output;
- an explicit explanation that enabling Props in a Look and showing the Prop are separate actions; and
- an OBS composite fallback for installations where ProPresenter's Web object is unreliable.

**Congregation → OBS Live Stream** uses the same searchable single-output-language workflow. Each OBS browser source or ProPresenter Prop carries one fixed language in its generated direct-IP URL. The OBS page no longer presents a hostname alternative or an unqualified legacy `/obs` address. Selections are remembered locally on the Operator computer, and dashboard polling updates the available language list only when it actually changes so an open selector is not interrupted. Changing a language visibly updates the address and tells the operator to copy it into, or refresh, an existing output. Both pages keep their short setup steps closed by default and place the full-guide action at the top of the expandable instructions.

The ProPresenter menu no longer carries a Beta badge. A representative 60–90 minute rehearsal on the church's actual ProPresenter computer, video input, Look, and network remains a v0.9.0 release gate.

## Data path

ProPresenter loads a local address such as:

```text
http://CHURCH-CAP-IP:8080/propresenter?lang=fr
```

The presentation page takes its language only from the URL. It does not inherit a previous phone-viewer language from browser storage and does not guess from the browser locale. The browser identifies its caption socket as a ProPresenter presentation client.

The broadcast hub keeps three concerns separate:

1. all connected caption sockets;
2. real congregation viewers used for viewer totals; and
3. clients that create translation demand.

A ProPresenter, OBS, or Room Display connection does not increase congregation viewer totals. A translated presentation does create translation demand, ensuring the selected language remains scheduled even when no phone currently requests it. The existing active-language capacity and translation safety policies still apply.

## Security and privacy

- Caption transport remains on Church Cap's existing local HTTP/WebSocket server.
- No ProPresenter credentials, API calls, cloud services, analytics, or outbound connections are introduced.
- The public overlay receives only the existing public translation state.
- Presentation connection diagnostics are available only through authenticated operator status.
- `/obs` continues to avoid opening a translated-audio/TTS socket.

## Compatibility

- Existing `/obs` addresses remain valid and default to English.
- Existing audience and Service Leader connections retain their previous viewer-count and translation behaviour.
- The Operator dashboard's English preview is explicitly a non-counted observer, so merely opening the dashboard no longer adds a congregation viewer.
- `/display?lang=CODE` and `/obs?lang=CODE` use deterministic fixed-language presentation output.
- OBS, Room Display, and ProPresenter connections are reported separately.
- If ProPresenter Web objects prove unstable on a specific installation, operators can composite Church Cap in OBS and pass the result to ProPresenter as a Video Input.

## Factory reset and setup recovery

The native macOS and Windows shell includes a separate factory-reset action under Updates and recovery. It is disabled during live captions and requires the operator to type `RESET`. The shell stops the engine before it stages and removes only Church Cap's known mutable application-data directories, then writes a reset marker, restarts the engine, and opens the complete setup flow. The bounded reset list includes settings, credentials, transcripts, logs, exports, translation models, Whisper caption models, spoken-audio packs, installer caches and the optional Windows CUDA runtime. Packaged model caches are explicitly rooted beneath Church Cap's application-data directory, so reset never needs to delete a cache shared with another application. Installed-language detection therefore cannot silently shorten a clean onboarding test.

Linux uses `./factory-reset-linux.sh` after the CLI server has been stopped. It applies the same bounded reset implementation and confirmation phrase, then the normal Linux start command opens setup. The password-only recovery path remains separate and preserves configuration and models.

Factory-reset setup ignores legacy `.env` credentials while its marker is present, prevents legacy project-local configuration from being migrated back into the fresh data directory, and clears Church Cap browser storage on the first reset setup page. The marker is removed only after the full setup has saved successfully.

First-run setup saves a translated language pack with the documented default of **Automatic** language availability, `most viewers first` priority, and an allowed list of English only. Once the pack's install is validated, visitors can choose any of its languages and the active-language limit manages load. Restricted mode therefore starts empty and only ever contains languages the operator ticked. Earlier v0.9.0 candidates saved Restricted with every pack language pre-ticked, which made Restricted appear not to restrict anything and made "selected languages first" degrade to alphabetical priority; the owner reproduced this on 2026-09-20.

Translation policy changes are also live state rather than browser-cached configuration. Saving Automatic or Restricted mode broadcasts fresh viewer metadata to connected audience pages, and `/api/languages` is explicitly served with `no-store` headers. Restricted mode therefore takes effect without requiring visitors to clear their browser cache.

## Server lifecycle and settings durability

The v0.9.0 native supervisor now uses the mutable-data root documented for source and script installations: `~/Library/Application Support/Church Cap` on macOS, `%APPDATA%\Church Cap` on Windows, and `$XDG_DATA_HOME/church-cap` (or `~/.local/share/church-cap`) on Linux. Engine start, password recovery, and factory reset share that one canonical path.

This is a change for desktop users, not a return to an earlier location. The public v0.8.0 Mac and Windows wrappers, and every v0.9.0 candidate before application-source commit `9a3ec57`, resolved their data directory with Tauri's `app_local_data_dir()`, which is `~/Library/Application Support/org.churchcap.desktop` on macOS and `%LOCALAPPDATA%\org.churchcap.desktop` on Windows. Switching roots without carrying that folder across made a normal update start on an empty data directory: no operator password, so complete onboarding was forced, and the previous languages, models, voices and transcripts appeared lost. The owner reproduced exactly this on the `9a3ec57` candidate on 2026-09-17; the sequence is recorded in [the lifecycle and settings handoff](V0.9.0_SERVER_SETTINGS_PERSISTENCE_HANDOFF.md).

The supervisor therefore migrates the pre-v0.9.0 folder once, before spawning the engine. `recovery::migrate_legacy_app_data` runs only when the canonical `data/` holds no `operator_auth.json`, no `factory_reset.flag` and no `legacy_data_migration.json`, and the legacy folder holds an `operator_auth.json` or `runtime_config.json`. It resolves the legacy path with the same `app_local_data_dir()` call the old builds used, so the location matches on each platform. The known top-level directories are renamed whole where the canonical root lacks them and merged one level deep where it does not; a colliding file inside `data/` is set aside with a `.pre-migration` suffix rather than overwritten, and colliding models or caches stay in the old folder. Any failure rolls every step back and fails the start with a clear message, so the engine never begins onboarding over a half-moved installation. The completed move is recorded in `data/legacy_data_migration.json` and a note is left in the old folder. Factory reset also clears the known directories from the legacy folder, so an old password file and downloaded models do not outlive a reset. Regression coverage lives in `recovery.rs` (seeded legacy root, guard conditions, merge, rollback) and in `tests/test_cross_platform_structure.py`, which now asserts that the migration precedes engine spawn rather than forbidding `app_local_data_dir()` outright.

Runtime settings are written to a same-directory temporary file, flushed, and atomically replaced. A last-complete backup protects language, audio, performance, privacy, and theme settings from an interrupted write. Windows replacement retries tolerate short antivirus or indexing locks without weakening the primary-save result. Manual native restart no longer discards a failed second start: the supervisor publishes a recovery-required state and the underlying error instead of leaving the controls in an ambiguous stopped/starting state.

Release verification includes the authenticated `/api/translation` save path plus a real frozen-engine two-cycle test. The latter starts the engine, reads a Restricted English/French audience policy, shuts down through the versioned supervisor protocol, starts again with the same isolated data directory, and confirms the identical policy and clean `starting → ready → stopping → stopped` lifecycle. Run it against each frozen platform engine with `scripts/release/check-settings-restart.py`.

## Verification

Automated coverage includes deterministic presentation language selection, public-context safety, translation demand without viewer-count inflation, presentation-kind reporting and TTS isolation. Before release, run the full automated suite, repository-hygiene checks, browser JavaScript parsing, visual checks in both themes, and a real service-length ProPresenter rehearsal.

The [v0.9.0 dependency audit](V0.9.0_DEPENDENCY_AUDIT.md) records the Python reachability controls and the compatible Rust lockfile updates that removed four disclosed desktop dependency vulnerabilities. The Rust audit is also enforced in CI.
